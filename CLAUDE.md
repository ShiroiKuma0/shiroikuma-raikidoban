# 白い熊 雷起動盤 (shiroikuma-raikidoban)

白い熊's personal fork of LightningLauncher (TrianguloY → pierrehebert), re-branded to install **side-by-side** with the original. Address the user as **白い熊**, never "user".

- **Language/UI stack:** legacy **Java + Android Views** (NOT Compose/Kotlin-first). Some newer files are Kotlin.
- **Modules:** `app/llx/app` (the app) and `app/llx/core` (shared). Build root is `app/llx/`.
- **R classes:** core code uses `net.pierrox.lightning_launcher.R`; app code uses `net.pierrox.lightning_launcher_extreme.R`. The `namespace` stays `net.pierrox.lightning_launcher_extreme` (never rename — code imports it). `applicationId` is `shiroikuma.raikidoban`.
- **App label:** 「白い熊 雷起動盤」.

## Build & ship

Use the **`build-apk` skill** — it has the full procedure. In short: `cd app/llx && JAVA_HOME=~/android-build/jdk17 ANDROID_HOME=~/Android/Sdk ./gradlew buildApk < /dev/null`. The task bumps `BUILD_NUMBER` in `app/llx/gradle.properties` and writes `~/tmp/shiroikuma-raikidoban_<versionName>_arm64-v8a.apk` (extreme/debug, arm64-v8a only).

**Never build a version twice.** The `+N` counter is **always** in the version name and **always** zero-padded to three digits (`14.3.7+001`), for releases as much as for throwaway builds — publishing tags `<VERSION_NAME>+<NNN>`, never a bare `14.3.7`, and the counter keeps running across version bumps instead of resetting. `app/build.gradle` floors it at 1, so a stray `BUILD_NUMBER=0` means "next build is `+001`". *(2026-08-11: the old "`0` = published, no suffix" rule made a build re-emit the released `14.3.7` APK name and its versionCode `3370000`.)*

**Hard gate (every build):** after a successful build, the only device action ever offered is an `adb push` to `/sdcard/tmp`, and only after asking. Never `adb install`/deploy/launch. After pushing, **wait** — 白い熊 installs and tests. Commit + `git push origin main` **only** when 白い熊 replies with the literal word **`Push.`** (anything else = keep fixing). Branch: work on `main`; PRs target `developer`.

## Conventions

- **Black-yellow everywhere.** All chrome = black background, yellow text/border — including toasts/flashes. Use `app/.../util/Flash.java` (not `Toast.makeText`). Colours now flow from the appearance config (below); default = `#000000` bg / `#FFFF00` text / `#FFFF00` accent (the accent was orange until 2026-08-10; `@color/color_primary`/`color_accent` match it). The edit-mode toolbar is translucent yellow (`eb_bar_bg` and friends in `app/.../values/colors.xml`) with black button text.
- **The app is permanently in night mode.** The stock light palette must never be reachable: `ResourceWrapperActivity.attachBaseContext` pins `AppCompatDelegate.MODE_NIGHT_YES`, and `UiConfig.applyUiConfiguration` forces `UI_MODE_NIGHT_YES` into the base `Configuration` (activities **and** `LLApp`, so app-context inflation is dark too). The black-yellow resource overrides live in `core/.../res/values-night{,-v28}/`, so anything landing in `values/` light chrome is a bug. Never give a style a `Theme.AppCompat.Light.*` parent — use `…DayNight…`. The stock "Application style: Light/Dark" preference is removed (`Customize.loadGlobalConfig`); `SystemConfig.appStyle` defaults to `DARK` and nothing reads it. *This was the root cause of the 2026-08-10 "a fresh install is white and orange" report: `appStyle` used to default to `LIGHT`.*
- **Typography in prose/replies:** end sentences with periods, curly quotes “ ” ’, en/em dashes, quote file paths — but keep code/paths/identifiers literal.
- **Verify the mechanism before fixing.** Confirm the real root cause against ground truth (read device data) before building a fix; first guesses here have been wrong more than once.

## Major subsystems (where things live)

- **Appearance config — 「白い熊 雷起動盤 UI」** (top of Lightning Settings): `core/.../configuration/UiConfig` (SharedPreferences "llui"), `UiSlot`/`UiGroup`, `UiTheme` (colour cascade + font apply), `UiFonts`; screen `app/.../activities/UiSettingsActivity`. Applied **per-render-point** (NOT via theme/resource override — the `ResourcesWrapper` is unreliable): bubble menus (`Dashboard.applyBubbleChrome`/`styleBubbleItemText`), dialogs (`util/UiDialogStyler`, `ActionsOverviewDialog`, `FoldMatrixActivity`, `Flash`), preferences (`LLPreferenceListView`, `feature/settings/LlPreference`+`LlPreferenceCategory`), toolbars (`util/UiChrome`). System bars are themed in `ResourceWrapperActivity` (gated by `themeSystemBars()`, which the wallpaper home/`Dashboard` overrides to false).
  - **Borders + corners:** `UiConfig` also stores per-slot border width (dp) and corner radius (dp); `UiTheme.borderWidthDp`/`cornerRadiusDp` (defaults: 2 dp border, 6 dp corner). `DIALOG_BORDER` frames every themed dialog panel via `UiDialogStyler.panelBackground` (also the full-screen `EventActionSetup` "List of actions" window; `AddItemDialog` self-applies it in `onStart`). **`MENU_BORDER`** (MENUS group; default 2 dp / 8 dp corner) frames the bubble/menu panel — painted at runtime by `Dashboard.applyBubblePanel` (rounded `MENU_BG` fill + stroke in an 8 dp `InsetDrawable` for the arrow gap), replacing the old static `bubble_bg` stroke. A **`BUTTONS`** group (`BUTTON_BG`/`BUTTON_TEXT`/`BUTTON_BORDER`, the last carrying width + corner) is painted by `UiChrome.applyButton` (e.g. the `BackupRestore` buttons). Sliders start at 0. New labels go in `values/` + `values-{ja,cs,ru}`.
  - **Every dialog goes through `core/.../util/UiDialogStyler`** (it lives in **core** since 14.3.6, so core dialogs reach it too; `style(Dialog)` finds its views by id, AppCompat's `AlertDialog` included). Framework dialog → `UiDialogStyler.show(builder)`, or `return UiDialogStyler.styleOnShow(builder.create())` in `onCreateDialog`; a dialog class of ours → `UiDialogStyler.style(this)` in `onStart()`; a plain `Dialog` → `stylePanel(this)`; one that needs its own `OnShowListener` → call `style()` from inside it. Never `builder.show()` / `builder.create().show()` — that is exactly the bare, borderless dialog. `ExportImportPanel` is the one exception (transparent window, own bordered box). Progress spinners use `util/ThemedProgressDialog` (`show`/`create`/`setMessage`) — no framework `ProgressDialog` remains.
  - **Text nobody paints is WHITE** — nothing overrides `android:textColorPrimary` (values-night only sets `colorForeground`), so a platform layout (`simple_list_item_1`, `setItems`/`setSingleChoiceItems` rows, `?textAppearanceLarge`, an `EditText`) draws white on our black. The net is **`UiTheme.paintUnstyledText(View, UiSlot)`**: it repaints every `TextView` still carrying a platform default (white / light grey — deliberate colours are chromatic or black and are skipped), leaves typefaces alone (icon fonts, font previews, monospace survive), and hooks each `AdapterView` with a hierarchy listener so rows are painted as they attach. `UiDialogStyler.style()` runs it over every dialog before the specific slots, so dialogs need nothing extra; non-dialog surfaces call it themselves (`EventActionSetup`'s action list, `BackupRestore`, `Shortcuts`, `StyleChooser`). A **spinner dropdown lives in another window**, out of the walk's reach — those use `app/.../util/UiSpinnerAdapter` (paints `getView` + `getDropDownView`).
- **Shortcut / action pickers & "app not installed" dialog:** `util/ThemedShortcutPicker` is the black-yellow replacement for the framework `ACTION_PICK_ACTIVITY` shortcut-app chooser (**白い熊 自由作業盤 / jiyusagyoban pinned first**); used by `EventActionSetup` and `Dashboard`. The "Select action" chooser (`EventActionSetup.addAction`) adds a synthetic **白い熊 自由作業盤 shortcut** (`PSEUDO_JIYU_SHORTCUT` → `pickJiyuShortcut`) + **Backup/restore** entries (negative sentinels → real `LAUNCH_SHORTCUT`). `AddItemDialog` also has a **白い熊 自由作業盤 ショートカット** item (`AI_JIYU_SHORTCUT` → `Dashboard.selectJiyuShortcutForAdd`). The Dashboard "app not installed" dialog (`DIALOG_APP_NOT_INSTALLED`) is a themed yellow list: Select app / 白い熊 自由作業盤 shortcut / 白い熊 雷起動盤 action (`EventActionSetup` as `CREATE_SHORTCUT`) / F-Droid (`f-droid.org/packages/<pkg>`) / Aurora Store (`market://`, `Version.APP_STORE_INSTALL_PREFIX`). (These all replaced the former Tasker shortcut entries — see the 白い熊 自由作業盤 bullet below.)
- **Localization (self-contained, in-app switchable):** Japanese/Czech/Russian are **bundled** in `core/.../res/values-{ja,cs,ru}/strings.xml` (extracted from the official LL language packs via `apktool d -s`). The external pack is **retired** (`LLApp.mLanguage = null`). The in-app Language picker forces the locale via `UiConfig.applyUiConfiguration` in `attachBaseContext` (+`applyOverrideConfiguration`) — do **not** use `AppCompatDelegate.setApplicationLocales` (no platform locale service on this device). Changing language does a **full process restart** and writes the pref with `commit()`. New strings → add to `values/` (English) and the `values-{ja,cs,ru}` you want.
- **Fold matrix** (replaces external Tasker fold logic for the tri-fold): `core/.../configuration/FoldGrid` + `app/.../activities/FoldMatrixActivity`.
- **Gestures overview** (long-tap → view/edit/clear event-action bindings): `app/.../util/ActionsOverviewDialog`.
- **白い熊 自由作業盤 (jiyusagyoban) integration** — sister app `shiroikuma.jiyusagyoban` (an OpenTasker fork, `com.opentasker.*`; source at `~/git/shiroikuma-jiyusagyoban`), the replacement for Tasker:
  - **Widget re-init/labeling** (`app/.../util/JiyusagyobanWidgets` + `Dashboard.setJiyuWidgetName`/`reinitJiyuWidgets`/`maybeOfferJiyuReinit`): headless name storage on tag `rkb.jiyuWidgetName`, dead appWidgetIds re-bound via the shared `Dashboard.rebindWidget`, name pushed cross-app by an ordered `…action.SET_WIDGET_NAME` broadcast. Menu entries live in BOTH the no-edit and **edit-mode** item bubbles (a live widget eats the normal-mode long-press); the bubble title shows the stored name on a 2nd line.
  - **Shortcuts:** the 「白い熊 自由作業盤 ショートカット」 picker entries (above) jump straight into jiyusagyoban's `com.opentasker.widget.CreateTaskShortcutActivity` (`ACTION_CREATE_SHORTCUT`); the result runs a task via `…/TaskRunActivity` (action `VIEW`, extra `com.opentasker.widget.TASK_NAME`). Such labels are prefixed 「白い熊 自由作業盤: 」 (string `acd_jiyu_prefix`) by `EventAction.decorateJiyuShortcutLabel` (core; idempotent; mirrors the kept "Tasker: <task>" label).
  - **Tasker is being phased out.** The Tasker Widget V2 re-init subsystem (`TaskerWidgets` + `TaskerWidgetAccessibilityService`), the Tasker shortcut entries, and the "data not ready" hint were **removed** (commit 141dd11). Still present: `sendTaskerIntent` scripting, the Tasker-plugin host (`Shortcuts` TS/TV), `PERMISSION_RUN_TASKS`, and the "Tasker: <task>" gesture label.
  - **Task shortcuts target the task's app** (`app/.../util/JiyuTaskTarget` + `Dashboard`): a run-task shortcut's component is always jiyusagyoban's `TaskRunActivity`, so "App info" / "App store" / "Uninstall" resolve the real app via the `com.opentasker.widget.TARGET_PACKAGE` extra, else an ordered `…action.GET_TASK_TARGET_PACKAGE` broadcast, falling back to jiyusagyoban.
- **Export / Import (the one backup) + 保存復元 automation** — `app/.../data/RkbExport` is the category-ZIP core: ONE zip per export named `shiroikuma-raikidoban_<yyyy-MM-dd_HH-mm-ss>.zip` (the 白い熊 family convention — every sister app's backups share one directory), `manifest.json` + one entry/tree per `Cat` (`ui` ⟨`ui.fonts`⟩, `settings`, `fold`, `desktops` ⟨`desktops.icons`, `desktops.wallpapers`⟩, `scripts`, `themes`, `variables`); file-based categories store paths relative to the engine base dir, so import is "strip the id, write under the base dir" (merge, never wipe; a restart is offered). The panel `app/.../util/ExportImportPanel` (bordered box, red-when-unset directory box, 全選択 + sub-options, ArcaneChat pill buttons) and the headless `app/.../util/StateExportReceiver` are its only two callers. The section sits **first on the 白い熊 UI page**, with the automation switch + token (`app/.../util/AutomationAuth`, own prefs file, never exported) directly under it. Directory = a persisted SAF tree in the `rkb_eximport` prefs (no All-Files-Access, so an absolute `path` extra is honoured only if that grant exists — else the configured directory, else `ERROR:no-storage-access`/`no-directory`). Contract: `<pkg>.action.EXPORT_STATE` / `.LIST_CATEGORIES`, one reply broadcast (no binders, `FLAG_INCLUDE_STOPPED_PACKAGES`), progress with real counts (`区分 n/N`).

## Device & debugging notes

- Target device: Huawei **Mate XT** tri-fold, **Android 12 / API 31** (HarmonyOS — no `LocaleManager`/`cmd locale`). Fold widths 1008/2048/2232.
- **The shipped APK is NOT debuggable** (`debuggable project.hasProperty("debuggableApk")` on the `debug` build type) — Android 15+ pops an "Android App Compatibility / debuggable app" dialog otherwise. Consequence: `adb shell run-as` does **not** work on a normally built APK. To inspect app data, rebuild with `./gradlew buildApk -PdebuggableApk` and install that.
- Inspecting app data: `adb shell run-as shiroikuma.raikidoban <cmd>` **DIRECT form** — the `sh -c '…'` form resets cwd away from the data dir. Globs don't expand (cwd is `/`). Needs a `-PdebuggableApk` build (see above).
- Config files under `files/`: `system` = SystemConfig (JSON), `config` = GlobalConfig (JSON), `pages/<id>/items` = per-page items (JSON). Widget provider/type are `"n"`/`"a"` fields; per-item gestures are `tap`/`longTap` under the item's `"i"`.
- This device **suppresses third-party `Log.d`**. To read another app's live UI tree use `adb shell uiautomator dump` + pull, not logcat.
- **Shortcut creators (`ACTION_CREATE_SHORTCUT`):** list handlers with `adb shell cmd package query-activities -a android.intent.action.CREATE_SHORTCUT`. jiyusagyoban's is `shiroikuma.jiyusagyoban/com.opentasker.widget.CreateTaskShortcutActivity`. (The former Tasker "data not ready" bounce detection in `EventActionSetup` was removed with the Tasker shortcut entry — commit 141dd11.)
- Always verify the **installed `versionCode`** (`dumpsys package shiroikuma.raikidoban`) before trusting a "still broken" report — a stale build has caused false alarms.
